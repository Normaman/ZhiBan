# 拼多多客服副驾驶：运行与验收

当前实现支持商家独立工作空间、多店铺切换和受邀客服协作。业务事实、平台连接和审批记录由 Spring Boot/PostgreSQL 管理；Python 只运行 Agent 编排，通过 Spring 内部接口读取商品、订单和店铺规则；React 提供审核工作台。拼多多登录和凭据由 Core 管理，详见 [账号与多店铺说明](multishop.md)。

## Docker 部署

Docker 首次部署步骤以 [README](../README.md) 为准。初始化后系统创建空白、未授权的拼多多店铺；管理员在工作台完成登录授权后才会建立连接。服务不注入样例商品、虚构咨询或自动成功发送。

合成商品、消息和订单只用于自动化测试与离线评测，不可从产品页面触发。

## 本地开发

本机运行在 WSL2。JDK 21、Maven 3.9 和 Node 22 位于 `~/.local/share/pdd-copilot/toolchains/`，shell 已配置 `JAVA_HOME` 和 PATH；新开终端生效。Python 使用已有 `~/miniconda3/envs/dl/bin/python`（3.10），不再使用项目 `.venv`。

```sh
conda activate dl
python scripts/dev.py start
python scripts/dev.py status
python scripts/dev.py restart --no-build  # 没有 Java 源码修改时
python scripts/dev.py stop
```

`start` 启动 PostgreSQL、Redis、Spring Boot、FastAPI Agent 和 Vite；`stop` 关闭三个应用进程，数据库保留运行。应用端口分别为 Java 8080、Python 8001、React 5173；开发数据库端口为 PostgreSQL 55439、Redis 56379，仅监听回环地址。日志、PID、数据库和加密执行日志保存在被 Git 忽略的 `.runtime/`。不得删除此目录后继续执行旧发送命令。系统使用单一工作空间；首次启动创建未授权店铺，不提供模式切换。

Java 默认使用 4 个后台执行线程，`WORKER_CONCURRENCY` 可设 1–16；队列权威仍是 PostgreSQL 持久任务表，短事务领取任务后在事务外调用 Python Agent。Python 允许最多 4 个不同生成任务并行，同一个 run 去重。真实平台连接和发送由 Java 管理。这里没有宣称已完成高并发压测，也没有新增 RabbitMQ/Kafka。

新环境依赖安装（当前 dl 已准备完毕）：

```sh
conda activate dl
python -m pip install -e 'services/agent-service[test]'
```

根目录 `uv.lock` 保留容器构建的可重复依赖；本地启动器不调用 `uv sync`，避免生成新的环境。共用 dl 时升级依赖前保留环境快照，当前安装没有升级原有深度学习依赖。

## 邀请码注册

登录页切换「邀请码注册」，填写账号、密码、确认密码和邀请码。账号限 3–48 位字母数字及 `_.-`，统一转小写；密码至少 12 字符且 UTF-8 编码不超过 72 字节。商家使用开通码创建独立空间；客服使用管理员在「店铺与成员」生成的一次性邀请码加入该空间。账号与 BCrypt 哈希存入 PostgreSQL `app_users`，密码不返回、不写日志。

商家开通码由部署者配置；客服邀请码绑定空间、48 小时有效、仅能使用一次、支持撤销，摘要保存在数据库。更换开通码只影响后续商家注册，不移除已有用户。目前没有邮件找回密码功能。首次管理员只在数据库中不存在时创建；修改环境里的密码不会重置已有账号密码。成员关系在每次业务请求重新核对，所选店铺 ID 不能作为授权凭证。

Redis 对每个直连来源地址每分钟最多允许 10 次注册尝试；开启后不可用会返回 503。反向代理部署下按代理地址保守限流，不信任客户端伪造的转发头；需要按实际可信代理配置调整后再服务更多用户。Redis 关闭时的内存限流只用于本地开发与测试。

浏览器通过 `POST /api/v1/auth/login` 建立 HttpOnly、SameSite=Lax 的服务端会话；Cookie 有效期 12 小时，刷新由 `GET /api/v1/auth/session` 自动恢复。浏览器存储不保存密码、Basic 凭据或登录令牌。修改请求带服务端返回的 CSRF token，登录切换会话 ID，退出使原会话失效。当前会话由单个 Java 进程保存，Java 重启需要重新登录，尚未迁移到共享 Redis 会话。脚本与监控保留 Basic 认证，内部接口仍用独立令牌。远程必须经 HTTPS，并设置 `SESSION_COOKIE_SECURE=true`。商家注册创建空店铺，但不会自动取得平台登录态。

Flyway 创建业务表。入站消息、运行结果、发送执行记录和执行租约统一由 Spring/PostgreSQL 保存；Python 不使用 SQLite 或本地持久运行目录。执行结果在返回 Worker 前写入 `agent_execution_results`，同一运行的重复请求复用结果。进程中断或模型计算完成但结果尚未提交时，租约到期后可能重新计算，不保证模型只调用一次。

## 真实拼多多测试账号

2026-10-27 已使用用户授权账号验证身份查询、Token、`m-ws` JSON WebSocket 认证、Ping/Pong、新消息入库与真实 DeepSeek 调用。认证成功值实际为 `auth.result="ok"`，本次响应的 `auth.uid` 是店铺 ID，不能当作客服 ID。商品查询最初返回 `3000000`，已通过复用正常商家页面生成的查询会话修复；已在一条用户指定测试会话验证人工文本发送成功回执，且买家确认只收到一条；这不代表其他店铺、失败分支或完整接待链路都已验收。

1. 在工作台的店铺设置中点击「连接拼多多」，授权页面会在新网页打开。Spring Boot 启动 Java Playwright 浏览器，并通过临时登录桌面显示；登录和平台验证均在该浏览器内完成，不需要在终端输入拼多多账号密码。
2. 回到授权页点击继续核对身份。系统通过当前登录 Cookie 向拼多多核验客服与店铺身份；确认店铺信息后再点确认保存。Cookie 以兼容 Fernet 的格式加密保存，授权页不会展示密钥或 Cookie。
3. 保存后 Spring 在 Java 内执行 WebSocket 认证核验并登记连接器。商品同步或订单详情读取需要查询会话时，Spring Java Playwright 会自动从正常商家页面生成并验证对应的只读会话。登录失败会显示明确状态，不会标记为在线。
4. 访问工作台确认「拼多多店铺」「拼多多已连接」「当前仅接收」。使用授权测试买家发一条新咨询；只能看到连接后接收的消息，没有平台历史拉取。平台 `system_hint` 通知会展示为「平台通知」，不触发 Agent，也不推进对话版本或覆盖买家咨询摘要。缺少商品/政策依据时由 Agent 提示人工处理。
5. 在「知识库」点击同步商品，保留本次平台商品快照。真实断线重连仍需单独验收；文本发送已完成一条授权测试的成功回执与买家接收核对。真实发送由 Spring Boot 发送服务执行，并受 `LIVE_SEND_ENABLED`、店铺与会话范围配置限制；Python Agent 不提供实时发送回退。仅修改本机 `.runtime/local.env` 不会改变 Docker 部署。实现沿用 `success=true` 且 `result` 无错误的判断，`10002` 识别为明确失败；其他不识别结果为 `send_unknown`，成功分支已有一次真实回执和买家接收验证，明确失败与未知结果分支仍未完成真实平台验收。

自托管者如明确需要对全部真实会话启用发送，可在 `infra/.env` 设置 `LIVE_SEND_ENABLED=true`、`LIVE_SEND_SHOP_ID=*`、`LIVE_SEND_CONVERSATION_ID=*`、`LIVE_SEND_EXPIRES_AT=-1`，再重建并重启 `core-service`。这只解除发送范围限制：Agent 草稿仍须人工批准，人工回复仍须显式提交；店铺离线、会话状态不符、审批版本过期及发送结果未知等保护继续生效。不要将这些授权值写入公开示例配置。

### 人工接待与真实发送联调

对话顶部「人工接管」暂停该会话的新咨询自动生成，显示独立输入框；「发送人工回复」提交人工确认的文本。人工回复不复用或覆盖 AI 草稿，每次提交带唯一请求号与会话版本，重复点击返回原记录。队列、连接器持久发送日志和回执机制与草稿审批共用。发送明确失败时，可点击「重试此回复」；新消息导致版本变化时需重新核对。结果未知时保持待核实，不能重试或恢复 Agent。

真实联调需先确认具体测试买家、对应会话及发送文本。以下操作只建立一条会话的发送权限，示例为限时模式，不自动提交任何回复。`会话编号` 是本工作台的内部 conversation ID，可从对应详情 API 取得，不能填写买家账号或平台消息 ID。

```bash
conda activate dl
python scripts/live_send_scope.py --conversation 会话编号 --minutes 30 --confirm-live-send
python scripts/dev.py restart --no-build
```

重新登录工作台，选中测试会话，查看对应会话的发送按钮或人工回复区权限提示。接管后输入已确认文本，点击「发送人工回复」，核对工作台回执和测试买家实际收到的内容；未验证前不扩大到其他会话。限时授权同时绑定默认店铺、指定会话和到期时间，两个服务在动作时检查有效期，到期后自动拒绝新发送。再次启动也不会延长到期时间，额外店铺保持关闭。经授权需要长期测试时，使用 `--persistent` 替代 `--minutes 30`；权限只对指定店铺的同一会话持续有效，服务重启后保留，直到主动撤销。持久授权使用明确的 `persistent: true` 和 `expires_at: -1`，缺失或零到期时间仍不开放。必要时立即撤销并重启：

```bash
python scripts/live_send_scope.py --disable
python scripts/dev.py restart --no-build
```

授权文件为 `.runtime/live-send-scope.json`，权限 0600；不包含 Cookie、买家消息或 API Key。当前没有全店发送开关或未知回执自动补发。本机已完成一条用户明确授权的测试发送，平台成功回执与买家接收一致；未验证全店发送、多店铺发送或真实故障重试。

```sh
python scripts/dev.py restart  # 使用单一工作空间重启
```

本地开发可用 `--live-data-dir /绝对路径` 指定 Core 的拼多多数据目录；登录身份和 WebSocket 由 Spring Boot 自动核验，不需要运行 Python 核验脚本。手工部署时需配置店铺绑定、数据库与 Core 的 `PDD_DATA_DIR`；平台凭据由 Spring Boot 管理。

商品同步失败会显示 `PLATFORM_PRODUCTS_UNAVAILABLE` 对应的页面提示，Agent 工具记录标记失败，不会以样例商品或空列表冒充平台查询成功。查询会话由 Spring Java Playwright 从正常商家页面生成，保存在 `product-session.enc`，使用现有凭据密钥加密并绑定店铺、客服与当前凭据摘要。服务端只在商品查询中使用；不生成校验签名、不提交聊天回复、不连接第二个聊天 WebSocket。会话过期时 Spring 自动重新获取一次。平台要求验证码时由用户在正常页面处理，助手不绕过验证。平台原始错误体和 Cookie 不进入日志。当前协议运行时不包含 Titan 二进制解码器。

发货或运费查询若发现商品详情与运费模板均无可用资料，会自动从正常商家页面刷新一次商品查询凭据并重查。仍没有资料表示本次平台响应无法确认该商品设置；应检查具体商品的发货配置与运费模板，不能用全店规则代替。

平台明确返回会话过期错误码 `43001` 时，连接器标为 `failed / PLATFORM_SESSION_EXPIRED` 并关闭旧连接。在线时每 60 秒检查 HTTP 登录身份，不能只凭 WebSocket 心跳显示长期在线。网络重连耗尽则保留对应失败原因；不把一般接口失败都判断成凭据过期。同一测试账号只允许一个连接器实例接待。

需要手动诊断具体订单状态时，从已授权测试订单卡片查看状态与缺失字段。Spring 遇到无效或过期的订单查询会话时，会在正常商家订单详情页重新捕获，只允许身份和订单详情读取，并阻断聊天 WebSocket；不会操作发货、退款或催单。正常页面要求验证时仍需操作员处理。

订单状态查询会话由 Spring Java Playwright 从正常商家订单页生成。遇到 `ORDER_SESSION_EXPIRED` 时，连接器会自动刷新并重试一次；若店铺登录也失效或刷新失败，才需要人工重新核验登录。`ORDER_SESSION_REQUIRED/INVALID` 表示无法载入有效的查询会话，不一定代表聊天登录失效。订单基础归属已核验但状态读取失败时，保留基础资料、标记状态未知，禁止用一般发货规则承诺该订单的发货。

订单查询会话自动更新失败后，检查店铺主登录态；若主登录也失效，从工作台重新打开授权页面并核对同一店铺和客服身份。运行中的 Java 连接器会检测凭据变化并重新认证，无需重启服务。服务不绕过验证码、不自动完成登录，恢复连接不重发旧回复。平台为何撤销某次会话以及登录态有效期仍未知，不能保证平台永不使其失效。

## 模型与知识

转人工后在会话顶部选择「恢复 Agent」，原会话继续使用，不创建新会话。恢复后自动处理后续新咨询，也可点击「重新生成草稿」处理当前未批准发送的问题；旧草稿和旧审批不会重新发送。会话有新版本时恢复返回 409，刷新再操作；存在未核实的发送结果时先人工核实。恢复不绕过退款、投诉等人工处理规则，也不等同于平台客服分配。

会话列表的未读徽标来自当前账号的 `message_reads`，不再固定显示红点。仅页面位于前台、会话已展示时确认这些消息 ID；其他客服的未读独立保留，后续新消息不会被旧请求一并清除。客服回复显示「已发送 · 买家已读/买家未读」，阅读状态来自平台 type 20 回执，按平台消息编号匹配，旧回执不能使已读倒退。缺少编号、没有回执或不在回执支持区间时显示「阅读状态待核实」，悬停可查看具体原因。发送成功只代表平台接受，不等于买家已读。当前不反向调用平台 `mark_read`，因此工作台查看不会改变拼多多商家端的未读列表。

未配置模型时使用规则识别、检索、原文摘录，工作台明确标注“未调用模型”。配置 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 后，启用从上游迁移适配的多轮工具 Agent：模型可自主选择只读商品/知识工具，再基于工具结果生成自然语言草稿，经引用与依据检查后交人工审批。详见 [Agent 编排与配置](agent.md)。

管理员日常在工作台「模型配置」保存自己的接口地址、模型和 Key，测试后启用；无需重启。`.env` 中原有模型字段仅保留为部署初始化兼容配置。没有真实 Key 时不会调用外部模型，协议夹具测试不代表模型质量验收。模型失败或检查拒绝会转为人工处理提示，不静默声称生成成功。

模型输出的引用必须对应实际检索来源；模型二次依据检查不保证事实绝对正确，仍须人工核对。高风险问题先由代码门禁拦截，发送能力不作为工具暴露。启用后，必要的会话文本和检索依据会发送给指定提供方；由店铺确认提供方数据保留策略。默认关闭 LangSmith tracing。不包含平台售后自动操作或图片模型调用。

「知识库」发布完整不可变版本，旧任务继续使用原版本。文档导入的格式、解析限制、同名替换和来源追溯见 [资料导入说明](knowledge-import.md)。商品同步保留平台商品快照；价格和库存问题另查询当前连接器，并在引用中记录获取时间。缺失库存是未知值。商品扩展知识需经人工核实后发布，不从图片抽取结果自动生成政策或商品事实。

## 可靠性边界

- 入站提交在数据库事务中完成消息唯一约束、任务创建和审计；相同消息重复提交返回原 ID，冲突内容返回 409。平台消息 ID 的跨账号唯一性仍需真实账号验证。
- 缺少平台消息 ID 时保留消息，停止自动生成；不以文本内容哈希冒充平台唯一 ID。
- 新消息增加会话版本并使未批准草稿过期；审批核对草稿和会话版本，同一版本的相同决定可以重放。
- 审批记录与发送任务同事务写入。任务通过持久租期恢复，执行结果通过 claim ID 防止过期 worker 覆盖。
- Spring 再核对审批命令、店铺、买家、最终文本和版本；调用平台前持久记录 `sending`。
- Spring 重启时把未完成发送标记为 `send_unknown`。同一成功或不确定命令不会重复调用平台。明确失败只有通过人工重试接口递增 attempt 后才会再尝试。
- 不提供无法证明的端到端 exactly-once 承诺。平台处理成功、HTTP 回执丢失时需要人工核查。
- 当前支持多个绑定店铺、多个受邀审核员；每个真实店铺由 Spring Java 连接器持有连接。
- Redis 提供跨 Java 实例的注册限流；业务幂等依赖 PostgreSQL 唯一约束和事务，连接器恢复依赖持久日志。

## 可观测性

Spring：`/actuator/health`；全局 `/actuator/prometheus` 仅允许原默认空间的管理员认证，其他商家及普通客服不能读取。Python：`/health`；`/metrics` 需要部署级 `X-Internal-Token`。不应把内部指标端口直接发布到公网。

指标包含任务类型及完成/失败计数、Agent 操作结果和框架 HTTP 指标。工作台显示连接状态、Agent run 状态、知识版本、审批与发送状态；审计页使用 run/approval/send command ID 关联记录。Python 请求响应带 `X-Trace-Id`，业务日志不记录消息正文、Cookie、Token 或原始平台错误体。平台凭据和连接事件由 Spring Core 管理；Agent 状态卷与平台凭据卷分开。归档与清理需按数据留存要求执行。

当前已实现空间和店铺权限隔离，仍面向本机/隔离测试部署；公开上线还需完成数据脱敏与留存、成员生命周期、额度与负载测试及多实例部署验证。远程部署须配置 HTTPS，告警规则和采集说明位于 `infra/monitoring/`。

## 商品与会话图片

已观察到的商品查询返回 `thumbUrl`；真实商品来源通知 type 41 的 `info.goods_info` 包含 `goods_id`、`goods_name` 和 `goods_thumb_url`。连接器将这些已核实字段提取为独立的内部 `media`，不改写消息正文、不改变平台通知动作，也不猜测 `total_amount` 的价格含义。V7 为消息增加可空媒体字段；首次补充旧记录的图片不增加消息、会话或 Agent run，已有媒体信息发生冲突时拒绝覆盖。

type 41 的 `pre_msg_id` 明确指向相关买家消息，V16 将其保存为 `related_platform_message_id` 并建立索引。卡片即使显示在问题下面，也优先用于其关联的问题。升级不会仅凭时间邻近给旧问题猜商品；历史补链须从已保存的原始平台事件核验。每件数量缺失时，在知识库新增「商品知识 / 商品规格」并绑定具体商品，经商家确认填写销售单位，不能把库存字段写成每份数量。

会话展示图片卡片，知识库中的平台商品支持缩略图、搜索和分页；图片加载失败显示占位提示。只展示 HTTPS 拼多多图片域名白名单内的资源，点击可查看原图。不通过服务器任意抓取外部地址，不将图片 URL 自动交给外部模型。商品详情同步会保存平台返回的主图与详情图片；当前没有视觉 Agent，商品规格不能从图片推断。

### 店铺标识与商品详情

顶栏「店铺」选择框切换已添加店铺，旁边「管理店铺」进入店铺与成员页。该页显示平台店名、头像和主营类目；修改名称只修改本工作台别名。当前只有一家店铺时不会出现其他可切换项。添加第二家店铺后还需在部署端使用独立登录目录完成对应拼多多授权，操作见 [多店铺说明](multishop.md)。

「知识库 → 同步商品」取得本店商品列表后，会检查详情缓存，仅排队补齐新增、变化、过期或之前未完整取得的分类、参数、规格和详情图片。已有商品列表可单独点击「同步分类与规格」，页面显示后台进度；服务重启后继续处理持久任务。后台任务按店铺限速，审批发送与草稿生成优先处理。只读接口发生暂时错误时按任务机制有限重试，最终失败保留明确状态，可重新同步。

完成后可按分类筛选，点击「查看分类与规格」检查参数、规格价格和库存快照及图片。库存必须结合显示的同步时间判断，不能作为实时承诺；平台未返回参数时明确显示缺失。查询会话过期时按上文商品会话准备步骤刷新，再重新同步。后台商品同步不调用发布、编辑或上架接口。

默认复用 6 小时内、基础列表指纹一致且参数查询完整完成的详情。列表核对仍需调用平台列表接口；已观察接口没有可靠的商品变更版本，分类或规格单独变化可能不反映在基础列表中，此时可点「强制刷新详情」。检查进度显示更新、复用、失败数量与本次检查时间；复用不会改写详情获取时间或旧库存快照。后台只保存平台图片地址，图片由浏览器按需加载及使用浏览器缓存。

会话持久化参考 [Spring Security 官方说明](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/session-management.html)，CSRF 处理参考 [官方 CSRF 文档](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

## 部署上线边界

React 静态资源、Spring Boot、PostgreSQL、Redis 与 Python Agent 可以部署到 Linux；Compose 会为授权登录准备 Chromium、虚拟桌面和 noVNC。授权桌面通过工作台同源路径和 WebSocket 代理提供，管理员使用任意可访问工作台的现代浏览器即可，不要求客户端安装 WSL 或 Python。不要把容器的 6080 端口映射到公网。WSL 的 dl 仅为本地开发环境，云端不需要复用整套深度学习环境。

公网部署还需部署者配置域名、TLS、密钥注入、持久卷备份及恢复验证。当前没有执行云端发布，也没有实际构建/运行 Compose 镜像（本机缺少 Docker daemon 权限）。真实拼多多链路必须完成隔离账号验收；部署前仍需在隔离账号上完成拼多多连接链路验收。

VS Code 建议安装工作区推荐的 Extension Pack for Java 与 Spring Boot Extension Pack，选择「安装到 WSL」。插件帮助补全、调试和测试，并不是服务启动依赖。Java 主业务包按 `api → service → repository` 分层，后台任务和外部调用分别位于 `job`、`client`。详见 [代码导览](code-guide.md)。


### 连续咨询合并与恢复

默认 `REPLY_DEBOUNCE_MS=2000`，固定最长合并窗口八秒。任务和待回复清单保存在 PostgreSQL，重启后继续认领；无需新增 Redis 队列进程。同一会话只持有一个有效生成租约，已有发送进行中或待核实时暂停下一批生成，避免重复答复。

收到多条咨询后，先核对右侧覆盖清单，编辑最终回复再审批。人工回复区直接输入并发送，不再展示咨询勾选；独立人工消息不自动清除待回复咨询。发送失败重试原命令，保留原覆盖清单；未知结果仍不可自动重发。旧版缺少覆盖证据的历史消息会列为待回复，升级不会自动生成或发送历史答案。
