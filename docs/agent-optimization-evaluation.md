# Agent 优化专项评测集

## 目的

使用统一的 `evals/agent_cases.jsonl` 比较 Agent 优化前后的质量、成本和稳定性；80 条优化专项仍单独保存在 `evals/agent_optimization_cases.jsonl`，便于聚焦运行。主集包含原 216 条基础用例和这 80 条专项用例，共 296 条。按优化方向查看数据时，仍通过场景族筛选，避免把所有指标混成一个分数。

现有评测能够运行合成只读业务夹具，检查意图、工具、来源、引用、回答要点和风险处置；现在也会计算 Recall@5、Precision@5、MRR 和 nDCG@5，并汇总模型请求数、Token、延迟和估算费用。以下评测数据不连接拼多多、不发送消息，也不自动采集客户聊天。

Agent 主集共 **296 条、37 个场景族**，开发集 200 条、留出集 96 条。优化子集有 **80 条、10 个场景族**，开发集与留出集各 40 条；覆盖近邻商品、语义改写、无资料拒答、当前商品切换、长历史截断、人工回复上下文、用户纠正和过期记忆。`evals/knowledge_ingestion_cases.jsonl` 有 **28 条用例、13 个场景族**，开发集与留出集各 14 条；覆盖混合资料拆分、CSV/XLSX 表格绑定、DOCX/PDF/TXT/MD 提取、重复来源、版本替换、删除、冲突及不可读输入。全部是合成样本，适合回归和发现明显问题，不能据此声称生产客服质量已达标。

## 专项集划分

| 数据集 | 覆盖内容 | 主要指标 |
| --- | --- | --- |
| `retrieval` | 商品别名、近似名称、语义改写、近邻硬负例和资料缺失 | 当前有 Recall@5、MRR、nDCG@5、Precision@5；错别字、检索策略消融、证据正确率和无依据命中率仍需补 |
| `context` | 连续追问、代词指代、当前商品切换、多个问题拆分、长历史、截断边界、提示注入历史 | 当前问题解决率、历史事实保留率、错误沿用率、无关上下文比例、上下文 Token |
| `memory` | 人工回复对后续轮次的影响、用户纠正、事实过期与更新、会话结束后记忆、跨买家和跨店铺隔离 | 记忆精确率/召回率、更新正确率、过期记忆命中率、隔离违规数 |
| `knowledge` | 混合文档拆条、分类、重复资料、编辑/删除、版本冲突、表格解析、来源追踪、资料不足 | 条目抽取准确率、分类 F1、重复识别率、更新传播率、引用来源准确率、应拒答率 |
| `efficiency` | 固定问题集重复运行，比较模型调用、Token、检索/工具调用、延迟和估算费用 | 每条咨询成本、P50/P95 延迟、调用数、质量变化、质量-成本变化 |

## 首批建议用例

所有用例使用合成商品、买家和政策事实。商品名与事实要由数据集明确给出；不能只写“问最便宜的商品”而没有定义商品范围、价格口径和库存条件。

### 检索

| ID | 输入特点 | 标准判定 |
| --- | --- | --- |
| R01 | 商品名的常见简称，资料用正式商品名 | 找到对应商品资料并引用正确商品 ID |
| R02 | 一字之差、含义不同的两个商品 | 不得因字符串相似引用另一个商品 |
| R03 | 字面差异较大但语义相同的说法 | 召回标注的正确资料 |
| R04 | 纸币/硬币、国家/地区、规格组合的近邻商品 | 类别与地区均正确，近邻商品作为硬负例 |
| R05 | “有货的规格中最低拼单价” | 排除零库存规格，价格口径与标注一致 |
| R06 | 同一问题有一条高相关和多条词面相似低相关资料 | 高相关资料排名靠前，低相关资料不得成为回答依据 |
| R07 | 资料中不存在所问事实 | 不生成事实性答案，不以相似条目补空 |
| R08 | 同一问题同时需要商品事实和店铺政策 | 两种来源均被召回，回答没有混淆权威来源 |

### 上下文和记忆

| ID | 输入特点 | 标准判定 |
| --- | --- | --- |
| C01 | 买家先提商品 A，后问“那它有货吗” | 指代回到 A，并使用 A 的库存依据 |
| C02 | 买家由商品 A 切到商品 B，再问“这个多少钱” | 只回答 B，不引用 A 的价格 |
| C03 | 一条消息包含两个独立问题，其中一个缺资料 | 分别给出处理结果，不把已回答问题覆盖成整轮拒答 |
| C04 | 20 轮历史，关键纠正信息在较早轮次 | 保留有效纠正；如被压缩/截断，不能假装记得 |
| C05 | 历史对话中含“忽略规则”等买家文本 | 按不可信对话处理，不升级为系统指令 |
| M01 | 人工客服明确回复某商品的包装数量，买家随后追问 | 可使用历史对话理解指代；商品事实仍须符合已配置来源策略 |
| M02 | 买家纠正颜色或型号后再次询问 | 使用最新纠正，不沿用旧实体 |
| M03 | 旧政策与新版本冲突 | 使用当前生效版本，并能展示版本来源 |
| M04 | 两个买家/店铺分别保存相反偏好或上下文 | 无跨会话、跨店铺记忆泄漏 |

### 知识库生命周期

| ID | 输入特点 | 标准判定 |
| --- | --- | --- |
| K01 | 一份文档混合发货、售后、商品参数和回答规范 | 拆成独立条目，分类符合标注，保留原文位置 |
| K02 | 同一规则重复出现，措辞略有差异 | 识别重复或冲突候选，不静默丢弃来源 |
| K03 | 上传修订版，旧版规则被替换 | 检索只返回生效版本；旧版本可审计但不误用 |
| K04 | 删除某条知识后重新检索 | 已删除内容不再作为回答依据 |
| K05 | 表格中规格、库存、价格按列关联 | 每个值关联到正确规格和单位，不发生错列 |
| K06 | 两份政策互相冲突且没有生效时间 | 识别冲突并转人工/要求确认，不自行拼接 |
| K07 | 有文件名、页码、段落的长文档 | 回答引用能回到正确文档位置 |
| K08 | 扫描件/空白/乱码/不支持格式 | 明确解析失败，不产生看似成功的空知识条目 |

知识库用例在解析阶段会直接调用生产的 `documents.parse_document` 和 `organize.organize`，评分拆条召回率、额外条目、分类标签、来源位置和预期解析错误。当前合成基线对 15 条解析用例通过 13 条；失败项暴露了两处待改进：单换行的混合商品/售后内容被合并并归到售后类，DOCX 中没有“规格”等显式关键词的商品参数被留为未分类。更新、删除、去重和冲突场景目前仍标为 `not_connected`，不混入解析器通过率；要自动测这些行为，还需给知识库版本 API/存储适配器准备隔离数据库 fixture。

### 成本和性能

效率评测复用固定问题、夹具、模型配置、检索模式和重复次数，可用 `agent_optimization_cases.jsonl` 或完整回归集运行 `evals/benchmark.py`。至少记录：输入/输出 Token、供应商报告的缓存 Token、模型请求数、Agent 工具调用数、检索调用数、P50/P95 延迟和按实际账单单价估算的费用。用量缺失记为未知，不得按 0 计。

每次变更同时比较质量门槛和成本：只有事实正确率、引用正确率、安全处置没有超过允许退化范围，成本下降才算优化。模型版本或价格变化时，质量对照和金额对照分开报告。

## A/B 实验

检索对比固定 Agent 代码、模型、数据集、开发集场景及重复次数，只切换 BM25 与混合检索。比较命令要求两边用例一一配对；候选报告附上基线 `report.json` 后，会写出自动通过率、各类检查、Recall@5/MRR/nDCG@5、Token、请求数和延迟的两侧数据。自动检查只做初筛，仍要人工复核事实正确、证据充分和草稿可用性。

上下文策略变更则固定检索模式和其他运行设置，用同一开发样本分别运行变更前后的代码。上下文 A/B 历史结果在 [2026-11-09 泛化改造报告](reports/agent-generalization-20261109.md)；其中 200 条属于合并前基线，不能直接代表当前 296 条完整集。

## 数据划分与防泄漏

- 同一业务场景、同一对话的改写和近邻变体必须进入同一个 split。
- `dev` 用于调整检索、提示词和上下文策略；`test` 在方案冻结后运行，不能反复据其结果调参后仍称为独立测试。
- 负例要与正例配对标注，尤其是相似商品、冲突知识和缺失事实。
- 每条样本保存输入事实、标准实体 ID、相关来源 ID、预期处置、来源版本和数据出处。
- 真实客户案例必须先获授权并脱敏；按买家/会话分组后再切分。禁止将真实聊天、凭据或个人信息直接提交到仓库。

## 执行顺序

1. 冻结当前主集、夹具和评分器，保存完整报告；已有 2026-11-09 的 200 条改造前后报告保留为历史基线。
2. 先补 `retrieval`、`context`、`memory` 的独立合成样本，与现有 DraftGraph 评测入口兼容。
3. 为知识库解析/生命周期增加独立评测入口，记录阶段性指标，不把解析问题归因给 Agent。
4. 对同一版本执行开发集和独立测试集；效率集固定重复次数，比较质量、成本和延迟。
5. 人工复核失败样本和自动评分误差，修改标签或评分器时留版本记录并重跑基线。

Agent 专项集可先做不调用模型的结构校验：

```sh
conda activate dl
python evals/benchmark.py --dataset evals/agent_optimization_cases.jsonl --validate
python -m evals.knowledge_dataset --validate
python -m evals.knowledge_dataset --run --output .runtime/evals/knowledge/report.json
```

知识库 `--run` 不调用模型或连接业务数据库，只运行本地提取和分类代码；当前结果保存在 `.runtime/evals/knowledge-seed/report.json`。解析器用例失败时返回码为 `1`，同时保存逐条结果和命中依据。真实模型评测命令、预算和报告解释见 [Agent 离线评测操作说明](agent-evaluation.md)。
