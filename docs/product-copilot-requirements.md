# 知伴电商副驾驶：知识库与商品发布助手需求

日期：2026-10-27。范围为当前单店铺产品，沿用 React、Spring Boot、Python/LangGraph，不新增微服务或替换已有编排框架。

## 产品目标

围绕同一份可信商品资料，服务两个高频工作：客服回答商品咨询，运营准备商品上架资料。先让商品、知识、审批和操作记录形成闭环，再接通经过授权验证的平台写接口。

| 使用者 | 主要任务 | 完成标准 |
| --- | --- | --- |
| 客服 | 确认咨询商品，查看依据，审核回复，必要时接管 | 不查错商品；不知道时说明缺什么；每条发送由人工批准 |
| 运营 | 整理商品事实，生成标题、卖点、详情文案及规格草稿 | 缺少的信息被列出，生成内容可追溯到输入资料 |
| 管理员 | 配置模型，发布知识，审批高影响操作，排查异常 | 能知道谁改了什么，失败原因和下一步操作明确 |

当前注册只区分管理员和客服。独立运营角色及商品发布权限是拟新增能力，不把现有客服角色直接变成平台发布权限。

## 本次问题及结论

库存咨询对应的实际 Agent 任务成功调用商品工具，但最终返回缺少依据；店铺快照中 145 件商品都有商品级 quantity，不能据此认定没有库存数据。代码检查发现：平台商品来源卡片的商品 ID 没进入 Agent 上下文；没有商品筛选条件时，工具只返回前五件商品；所有缺少依据又被统一改成同一句提示。

修复方向是先正确定位商品，再查实时数据。知识库是否为空不应阻止已经取得依据的商品级库存回答。商品接口没有取得具体颜色/尺码库存时，不能用商品级数量替代分规格数量。商品没有明确、平台接口失败、参数缺失、发货规则未发布，应分别显示不同原因。

## 参考的产品做法

- Gorgias 将平台商品目录、商品网页和商家补充资料结合使用，并让商家查看每件商品有哪些可用资料。这里借鉴“商品主数据＋补充知识”，不照搬其 Shopify 接口。[产品资料管理](https://docs.gorgias.com/en-US/manage-your-product-information-for-ai-agent-4036592)
- Gorgias 的客服 Agent 根据问题选择工具、补充信息，再检查回答依据。这里借鉴“实时工具与知识检索分工、生成后核验”，仍保持本项目人工审批发送。[Agent 工作方式](https://helpcenter.gorgias.com/en-US/how-gorgiass-ai-agent-works-1997817)
- Dify 的知识准备流程包括来源导入、分块预览和索引/检索配置，元数据可缩小检索范围。这里借鉴数据治理与检索流程，不把部署 Dify 当作当前任务前提。[知识准备](https://docs.dify.ai/en/cloud/use-dify/knowledge/create-knowledge/introduction)、[元数据过滤](https://www.dify.ai/blog/dify-v1-1-0-filtering-knowledge-retrieval-with-customized-metadata)
- Shopify 的商品描述助手根据商家提供的商品信息生成建议，商家编辑、核对后保存。这里借鉴先提供事实、再生成和人工确认的流程。[商品描述生成](https://help.shopify.com/en/manual/products/details/product-descriptions/generate)

这些是产品和流程参考，不代表当前代码已实现完整文档 RAG、视觉理解或自动发布。

## 客服知识应如何组织

| 数据层 | 应包含什么 | 权威来源与更新 |
| --- | --- | --- |
| 实时商品数据 | 当前商品级价格、库存；后续验证后加入分规格库存 | 平台只读接口。回答时查询，不把库存写进固定知识正文 |
| 商品资料 | 材质、尺寸、规格、使用方法、兼容范围、注意事项 | 商家核实的商品资料，绑定 goods_id；有 SKU 细节时额外绑定 SKU |
| 店铺规则 | 发货时效、适用地区、预售/节假日例外、售后条件 | 店铺确认后发布的版本，写明适用条件、生效时间和负责人 |
| 经审核问答 | 常见问题及核实后的回答、适用商品和引用来源 | 从客服处理记录提议，由负责人审核；买家对话本身不是事实来源 |

商品图片可作为素材或经审核的信息来源，但当前仅用于展示；图片中识别出的文字不能直接成为已发布商品事实。

### 现在可以使用的最小知识库

1. 从平台同步商品目录，人工补充资料时选择对应商品。
2. 一条资料解决一个问题，例如“某商品材质说明”“预售发货例外”；不要混放多件商品或不同售后条件。
3. 在知识库页面添加资料名称、类型、适用商品和正文；编号及版本由系统管理。
4. 支持 JSON 文件导入、预览、确认发布；同编号更新，旧版本保留。模板中的内容只是占位说明，不能作为真实政策发布。
5. 发货和售后没有真实规则时保持缺失，不自动填入“48 小时发货”等常见承诺。

当前检索仍是商品范围过滤和有限条目筛选，没有部署向量库、嵌入模型或文档解析流水线。DeepSeek 的文本模型配置也不等同于已经配置嵌入模型。

### 后续完整知识流程

`资料来源 → 解析预览 → 标准化与冲突检查 → 绑定商品/条件 → 审核发布 → 检索测试 → 生效与回滚`

- 来源：优先 CSV/Excel 商品参数、Markdown/文本规则；PDF 和网页需要解析及来源权限检查。图片 OCR/视觉识别进入待审核状态。
- 元数据：店铺、商品、SKU（如有）、来源、资料类别、适用条件、生效区间、版本、审核人、状态。店铺和商品过滤先于相似度召回。
- 分块：按标题、问题和规则条款分段，保留限制条件，不把“例外/不支持”截断到另一个无关联块。
- 检索：先做商品 ID 和结构化字段匹配；长文本增多后加入关键词＋向量混合召回，再按质量/成本决定是否增加重排。
- 版本：发布生成不可变快照；运行中的任务继续引用原版本；停用和回滚另记操作记录。
- 缺失治理：记录查不到商品、缺参数、缺政策、接口失败的原因，供运营补资料，不把全部失败统一计作“知识不足”。
- 检索测试：管理员输入问题，看到匹配商品、命中的资料和版本；测试输出不自动发布为知识。

新增向量检索前先确定嵌入模型提供方、中文效果、数据处理约定和真实评测结果。PostgreSQL 是否安装向量扩展、是否需要单独检索服务，以验证结果决定，当前没有安装或启用。

### 验收样例

| 场景 | 应有行为 |
| --- | --- |
| 当前商品明确，问“还有货吗” | 精确查当前商品，不从前五件随机取一件 |
| 商品不明确，问“库存多少” | 请求商品链接/名称，不要求用户新建库存知识 |
| 库存为 0 | 明确显示平台返回 0，不当成缺字段 |
| 库存字段缺失或接口失败 | 分别说明未知或查询失败，不编造有货 |
| 指定红色 M 码，但仅有商品级数量 | 说明未取得分规格库存，请核实该规格 |
| 询问材质但未录入商品参数 | 提示补充该商品参数，不能套用其他商品资料 |
| 问发货但没有已发布规则 | 提示店铺规则缺失，不套用未配置的通用政策 |
| 多份商品资料文本相似 | 先按商品过滤，再检索，引用正确商品与版本 |
| 退款、投诉、改地址、赔偿 | 继续人工处理，不因资料充足绕过门禁 |

## 商品发布助手需求

### 最小版本：先完成可审核的发布草稿

目标是把一份经过核实的商品资料整理成可供运营使用的上架材料。这个阶段不自动提交平台、不伪装“发布成功”。

| 步骤 | 输入/产物 | 必须检查 |
| --- | --- | --- |
| 创建草稿 | 商品名称、品类意向、品牌/资质（适用时）、参数、规格、素材 | 缺失字段明确列出；不知道的材质、品牌、功效不能补造 |
| 整理事实 | 商家确认的事实清单及来源 | 每条事实有来源；生成文案与事实分开存 |
| 生成文案 | 标题候选、卖点、详情文案和常见问答草稿 | 只改写表达，不变更商家填写的价格、库存或 SKU 事实 |
| 检查草稿 | 必填缺失、规格组合冲突、内容与事实不一致、需要资质的声明 | 类目和平台规则未核实的项目显示待核实，不能冒充校验通过 |
| 人工审核 | 编辑前后差异、事实引用、草稿版本 | 版本冲突返回 409；草稿更新使旧审核失效 |
| 导出资料 | 文案、规格表、素材清单、待核实清单 | 只导出人工确认的版本；运营在商家后台完成发布 |

应有页面：商品草稿列表；资料/素材编辑；生成结果与事实对照；问题清单；人工审核和导出。客服工作台继续专注咨询，不把商品发布表单塞进聊天侧栏。

### 后续版本：授权平台发布

拼多多商品发布需要重新核实开放平台接入资格、商家授权、具体权限、类目规则和真实接口契约。已有聊天 Cookie/WebSocket 能力不能证明具备商品发布权限。

尝试访问的[拼多多商品发布说明](https://open.pinduoduo.com/application/document/browse?idStr=EF2DB30A2A9C8FD7)本次未取得可读内容。因此本文没有断言具体请求字段、图片尺寸、类目属性模板或当前账号权限；这些均为接入前待验证项。

拟实现：

- 读取当前店铺授权可发布的类目和动态规则，再生成对应表单；不把某一类目的必填字段写死为通用规则。
- 素材与规格校验后，按最终审核版本建立唯一发布命令。
- 发送前核对店铺、权限、草稿版本和审核记录；平台提交后保存原始结果的安全摘要及平台标识。
- 区分“本系统已审批”“已提交平台”“平台审核中”“平台已发布”，HTTP 成功不等于商品已上架。
- 超时或结果不确定进入待核实状态，先查询平台状态，禁止自动再创建一件商品。
- 同步平台最终商品记录，再形成可审核的客服知识候选；生成文案本身不是库存、资质或功效事实。

### 状态与权限

最小版本：`资料不全 → 待生成 → 生成中 → 待审核 → 已确认 → 已导出`，另有生成失败、审核拒绝、版本过期。

平台发布版另增：`待提交 → 提交中 → 平台处理中 → 已发布/平台拒绝/结果待核实`。

普通客服默认没有商品发布权限；运营可整理草稿，管理员或授权负责人可确认发布。是否允许一人同时编辑和审核，由店铺配置，默认不允许后台任务自行批准。

### 发布验收

1. 只给商品名称时列出缺项，不生成虚构材质和功效。
2. 修改生成文案不改变人工录入的价格、库存、SKU 和品牌事实。
3. 相同规格组合不能重复；缺少实际类目规则时不能显示平台校验已通过。
4. 修改草稿后旧版本不能批准；普通客服不能越权提交。
5. 没有平台权限时只提供草稿/导出，不能出现虚假的发布成功状态。
6. 重复点击只创建一个发布命令；超时先核实，不重复创建平台商品。
7. 发布状态、操作者、版本和异常原因可在中文操作记录中追溯。

## 实施顺序与当前边界

| 优先级 | 工作 | 当前状态 |
| --- | --- | --- |
| 本次 | 常驻顶栏、中文操作记录、收简说明、改进知识录入 | 已修改，按验证记录确认验收 |
| 本次 | 商品来源上下文用于库存定位，缺失原因分类 | 已修改，需以对应测试及真实只读验证确认 |
| 下一步 | 商品资料完整度、缺失问题队列、检索调试 | 需求已明确，未实现 |
| 下一步 | 文档导入、清洗分块、混合检索及检索评测 | 需求已明确，未实现 |
| 下一模块 | 商品事实库、发布草稿、内容生成、审核导出 | 需求阶段，未实现 |
| 权限验证后 | 真实商品发布、平台结果跟踪与去重 | 尚未接入，不承诺已可用 |

先用真实店铺问题建立评测集，对商品定位、库存正确引用和政策条件逐项测试；再扩展知识规模和生成模块。商品发布助手的价值是复用商品事实和审核能力，不靠增加无实际链路的页面扩大功能数量。
