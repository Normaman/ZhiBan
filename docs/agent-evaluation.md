# Agent 离线评测操作说明

本次链路恢复改造的固定数据对照结果见 [2026-11-09 评测报告](reports/agent-generalization-20261109.md)，包含改善、退步、延迟、调用量和未解决问题。

面向后续检索、上下文/记忆、知识库和成本优化的专项评测设计见[Agent 优化专项评测集](agent-optimization-evaluation.md)。该文档区分了已有评分能力与需要新增的评测入口，避免把规划指标当成已实现指标。

Agent 主评测集 `evals/agent_cases.jsonl` 有 296 条合成用例、37 个场景族，开发集 200 条、独立测试集 96 条。它包含原有 216 条基础用例和 80 条优化专项用例；`evals/agent_optimization_cases.jsonl` 保留为这 80 条的便捷子集。用 `conda activate dl` 后运行 `python evals/benchmark.py --validate` 做离线结构校验。知识库集 `evals/knowledge_ingestion_cases.jsonl` 有 28 条合成用例、13 个场景族，开发集和留出集各 14 条。`python -m evals.knowledge_dataset --run --output .runtime/evals/knowledge/report.json` 会调用生产文件解析与规则分类代码并评分；版本替换、删除、去重和冲突用例仍标为未接入，不算作解析器通过。

## 只做人工复核：照这几步操作

1. 在 WSL 终端进入项目目录，启动校对页：

   ```sh
   cd ~/project/Customer-Agent
   conda activate dl
   python -m evals.workbench
   ```

2. 保持这个终端运行，在浏览器打开 <http://localhost:5190/review.html>。如果终端说服务已启动，直接打开网页即可。
3. 左侧先选「原评测未通过」；点一条用例后，在「回答对照」查看改动前后回答和依据。「测试资料与预期」可查看测试事实。
4. 认为某条自动判分有误，点「纠正自动判分」，只改选判错的检查项并保存；补充说明是可选的。要修改测试问题或预期，才使用「编辑用例」并填写修订说明。
5. 要保存一份可复用的新测试集，点「导出新版本」并填写版本名和修订说明。进度保存在 `.runtime/eval-curation/main/`，以后重新启动会继续保留。按 `Ctrl+C` 停止校对页。

判分校正和用例修改不会覆盖原始报告。改了问题或测试事实后，旧回答不能代表新用例；需要用新版本重新运行模型评测。顶部「重算已有结果」只重算原有回答的自动检查，不会调用模型。

只想复核时不需要启动客服系统、数据库或拼多多，也不需要配置模型。下面的内容是评测开发与复跑说明，可以先跳过。

评测运行真实的 `DraftGraph → 意图识别 → 只读工具 → 检索 → 草稿 → 依据复核`，但平台数据来自固定合成夹具。没有连接器发送方法，不接入真实拼多多、不给业务数据库创建消息，也不将客户聊天自动导入评测集。

## 三种检查不要混用

| 检查 | 命令 | 能说明什么 |
| --- | --- | --- |
| 原有基础回归 | `python evals/run.py` | 10 条无模型路由／证据类型检查，不代表模型回答质量 |
| 数据集校验 | `python evals/benchmark.py --validate` | 用例格式、ID、正则和场景分组有效，不调用模型 |
| 真实模型评测 | `python evals/benchmark.py --model-source ...` | 固定业务输入下的实际模型、工具、检索和自动规则结果 |

Playwright 检查审批、发送和页面流程；单元测试检查代码行为。它们与这里的模型效果评测互补，不能把程序测试通过率当作问答正确率。

## 数据集及边界

`evals/agent_cases.jsonl` 包含 **296 条合成问法，来自 37 个业务场景，每个场景 8 种表达**，不是 296 个独立场景。其中开发集 200 条、25 个场景，独立测试集 96 条、12 个场景；新增专项覆盖近邻商品、语义改写、长历史、人工回复记忆、用户纠正和过期记忆。同场景所有变体只属于一边，防止同义改写泄漏。

覆盖库存与销售单位、规格库存及最低价、普通拼单价、商品发货与预售、甘肃运费、正式 FAQ、退货条件、已取消／待付款订单、物流资料缺失、风险转人工、纯交流与混合问题、未知库存、缺资料、批次部分回答、提示词注入、已发送人工回复的上下文。

- 用例格式与标签在 `evals/dataset.py`，合成事实和只读连接器在 `evals/fixtures.py`。
- 每条标签定义允许的结果、意图集合、有效工具策略、必要来源、参数模式、回答要点和禁止的肯定断言。合法的商品列表与 SKU 查询路径可分别接受。
- Gold 标签只交给评分器，不进入模型提示词。原 200 条输入由 `question` 和 `fixture` 构造，订单、买家及商品均为合成数据；校对工具新增的 `custom` 场景从显式 `input` 读取模拟事实，可另行标注脱敏真实或公开资料来源。
- 商品来源关系从已经构造好的 Python 上下文开始；这里**不覆盖** Java 对原始平台卡片的解析和绑定、平台推送、发送去重、队列或真实连接可靠性。
- 数据集不是随机真实流量样本；其通过率不能直接推导生产满意度。后续扩充应单独获得授权并脱敏，按买家／会话分组，避免把同一对话分到开发集和测试集。

需要修改合成问法或标签时编辑 `evals/build_dataset.py`，再运行：

```sh
python -m evals.build_dataset
python evals/benchmark.py --validate
```

正式测试前冻结数据、夹具和评分规则。失败时先区分模型问题、夹具问题及评分误伤；不能为了提高分数静默修改标准。报告记录这些内容的哈希，不兼容的基线会拒绝比较。

真实模型运行会先复制 Agent、评测代码和数据到临时目录，再由独立 Python 进程导入该副本。工作目录中的后续代码修改不会混入同一轮执行。报告附带 `code-snapshot.json` 及源码哈希，结束时核对副本没有变化；若检测到修改，状态为 `source_changed`，不当作正常完成。配置和数据库仍使用部署端指定位置，但运行模式固定为合成只读连接器。

## 1. 准备模型配置

在项目根目录、Conda `dl` 环境操作。可以选择下列一种模型来源。

### 读取工作台已启用的模型

服务运行时，复制「店铺与成员」中的店铺接入编号，用 `--model-source admin --shop-id '店铺接入编号'`。评测器通过本机内部接口**只读取启用的模型配置**；不读取该店铺消息、知识库、订单或平台 Cookie。部署令牌从本机 `.runtime/local.env` 获取，不写入报告。

示例中的编号需要替换。新店铺没有启用模型时先在工作台保存、测试并启用：

```sh
python evals/benchmark.py --model-source admin --shop-id '替换为店铺接入编号' --split dev --one-per-scenario --limit 3 --max-model-calls 30
```

读取其他部署可指定 `--core-url` 和 `--env-file`。内部配置接口只能使用 HTTPS 或本机回环地址，不跟随重定向。

### 使用独立环境变量

不依赖工作台或拼多多登录，只需要支持工具调用的模型接口：

```sh
export LLM_BASE_URL='https://api.deepseek.com'
export LLM_MODEL='填写该密钥实际可用的模型名称'
read -r -s -p 'API Key: ' LLM_API_KEY
export LLM_API_KEY
python evals/benchmark.py --model-source env --split dev --one-per-scenario --limit 3 --max-model-calls 30
unset LLM_API_KEY
```

密钥不通过命令行参数传递。评测调用真实提供方，会使用 API 额度；开发时先限制用例和调用数。没有配置模型会明确失败，不自动退回无模型摘录或协议夹具。

## 2. 选择检索方式

默认 `--retrieval bm25`，只运行本地关键词检索，不需要数据库；报告明确记录为 BM25，不冒充向量检索。

使用 `--retrieval hybrid` 时，需要本机 PostgreSQL、pgvector、`rag` extra 和已下载的 BGE 模型，准备步骤见 [混合检索说明](hybrid-rag.md)。评测器创建单独的 `copilot_eval_*` 数据库，只存本次合成资料的派生索引，退出时删除；不连接真实业务知识索引。

模型权重在用例计时前加载，单条用例耗时包含其实际检索和索引构建；首条查询可能比后续慢。发生 `bm25_degraded` 时保留真实模式，并将该条请求的混合检索检查标为失败，不静默宣称混合检索成功。

## 3. 开发、重复与独立测试

开发时先每个场景取一条，重复运行检查波动：

```sh
python evals/benchmark.py --model-source admin --shop-id '替换为店铺接入编号' --retrieval hybrid --split dev --one-per-scenario --repeat 3 --max-model-calls 350 --output .runtime/evals/dev-repeat
```

完整开发集共 200 条：

```sh
python evals/benchmark.py --model-source admin --shop-id '替换为店铺接入编号' --retrieval hybrid --split dev --max-model-calls 900 --output .runtime/evals/dev-full
```

冻结实现后运行独立测试集，不用其失败样例反复调提示词后仍声称是未见测试：

```sh
python evals/benchmark.py --model-source admin --shop-id '替换为店铺接入编号' --retrieval hybrid --split test --max-model-calls 350 --output .runtime/evals/test-full
```

一次完整基线可使用 `--split all --max-model-calls 1800`，覆盖 296 条。还可用重复的 `--case inventory-01 --case published_faq-01` 指定用例，或用重复的 `--scenario opt_context_long_history` 选择场景族；跨集合选择需显式使用 `--split all`。

- 默认只跑 `dev`；默认最多发起 100 次模型请求，不是 100 条咨询。一次咨询通常包含多次请求。
- `--repeat` 为 1–10 次，`--limit` 限制问法数；调用预算跨用例和批次子问题共用，在请求发出前检查。
- 达到预算会停止，报告状态为 `budget_exhausted`；已完成结果仍在，不能把部分结果宣称为完整评测。
- 进程逐条运行，单条内部沿用生产的工具与批次并发；这里不是高并发压测。
- 输出目录不能已经存在，防止覆盖旧报告或人工标注。未指定时写入 `.runtime/evals/UTC时间/`。
- 返回码 `0` 为完成且自动规则全通过，`1` 为有失败、预算不足或源码副本变化，`2` 为参数／准备错误。`make test` 不自动触发付费模型评测。

## 4. 阅读报告

| 文件 | 内容 |
| --- | --- |
| `report.md` | 场景通过数、延迟、模型请求及失败用例概览 |
| `report.json` | 元数据、完整汇总和逐条结果；每条完成后原子更新 |
| `results.jsonl` | 买家合成问法、预期、实际回答、意图、工具参数、引用、逐项检查和 token 用量 |
| `review-template.jsonl` | 对应实际结果哈希的人工评分模板，初始评分为空 |
| `code-snapshot.json` | 本轮源码、SQL 和合成用例快照；不包含环境文件、API Key 或平台凭据 |

重点指标：

| 指标 | 定义与分母 |
| --- | --- |
| 自动检查通过率 | 所有标注检查均通过的执行次数／已执行次数 |
| 意图匹配 | 实际意图集合符合某个允许集合；只统计有意图标签的用例 |
| 工具及参数检查 | 是否用了有效工具路径、是否满足标注参数；不把一种合法实现固定为唯一答案 |
| 引用与版本 | 引用来自本次真实工具返回，知识版本匹配，商品来源不能串用 |
| Recall@5 | 标注资料是否出现在实际知识工具每次返回的前五项中；多次查询取并集，只统计标注了检索依据的用例 |
| Precision@5 / MRR / nDCG@5 | 对标注了 `retrieval_sources` 的样本，按评测报告记录的召回来源顺序计算；多次检索调用按来源首次出现顺序合并去重。属于小型专项集的检索排序诊断，不替代线上相关性人工审查 |
| 应答问题被拒绝 | 预期可回答的用例中，实际未产生草稿的比例 |
| 复核拒绝可回答问题 | 可回答用例中，结果带 `DRAFT_NOT_SUPPORTED` 的比例；须结合人工检查判断是否误拒绝 |
| 高风险生成草稿 | 风险标签用例中实际生成草稿的比例；分母为零时为空，不显示为零风险 |
| P50／P95 | 单次咨询的完整图执行耗时，不含模型权重预加载；不包含平台推送和工作台刷新 |
| 重复全通过 | 重复运行过的问法中，每次均通过的比例，不要求逐字相同 |

不同指标有不同分母。工具／引用等类别按检查项统计；不能将它们的分数简单平均成客服质量。自动检查使用正则和结构事实，仍有语义盲区，**不是幻觉率、满意度或人工可用率**。Agent 自己的 `supported=true` 也不是评测真值。

token 用量来自服务商返回的计数字段，只保留非负整数，不保存额外原始字段，也不将用量回放给模型。缺少用量的请求不会算成零消耗。需要金额估算时，按自己的账单价填写 `--input-per-million` 与 `--output-per-million`，两者同时提供且单位一致；不内置可能过时的价格，也不计缓存折扣。未给价格或用量不完整时金额为空。

## 5. 人工评审与不调用模型的重算

### 离线对照复核页

可从已完成的两份报告生成一个无需启动服务的 HTML 文件，不调用模型、不修改报告或原分数：

```sh
python evals/review.py --before .runtime/evals/generalization-before-20261109/report.json --after .runtime/evals/generalization-after-final-20261109/report.json --output .runtime/evals/new-review/review.html
```

在浏览器打开生成的文件。可筛选新版未通过、前后退步、风险咨询、每个场景随机抽取的一条通过用例，或全部咨询；左右对照问题、测试参考资料、实际工具结果、草稿引用和检索记录。抽样固定种子，只用于发现漏检，不代表真实流量抽样。

每个版本分别填写三项判断和说明，再导出对应的 JSONL。未填写完整的记录不导出，不预填“通过”；每条复核绑定原结果指纹，结果被修改或两份报告使用不同评分器时拒绝生成。浏览器本地保存填写进度，不向服务发送数据。它用于定位问题和人工复核，不是盲评界面，也不会将 AI 自评计入人工分数。

生成器 `evals/review.py` 和 HTML 文件均保存在磁盘，重启后仍可使用。评分进度保存在同一浏览器、同一访问来源的 `localStorage`，尚未写入 PostgreSQL；清理浏览器数据、换浏览器或将 `localhost` 改成 `127.0.0.1`／其他端口，都不会自动带上原进度。请导出 JSONL 作为文件备份及汇总输入；当前页面没有导入评分文件恢复编辑的入口。

这是旧版静态查看器。现在本机 `5190` 使用下方的数据集校对工作台，静态 HTML 仍保留，可直接打开。旧 HTML 的评分只在浏览器保存；工作台可以将同来源的旧评分迁入文件，且不覆盖已有文件评分。

### 本地数据集校对工作台

目标是维护可信的评测数据和人工判定，不是单纯提高通过率。它独立于客服业务服务，不调用模型、不读取店铺数据库、不发送拼多多消息，也不自动收集客户聊天。

在仓库根目录启动：

```sh
conda activate dl
python -m evals.workbench
```

打开 **http://localhost:5190/review.html**。只监听本机，不随 Docker 或开机自动启动；终端按 `Ctrl+C` 停止。默认载入本机 2026-11-09 的前后两份报告和原 200 条基线用例。首次运行会创建 `.runtime/eval-curation/main/config.json`、`workspace.json` 和冻结基线 `base-dataset.jsonl`；再次启动时，未显式传入 `--dataset` 就使用工作区冻结基线，因此后续扩充仓库数据集不会破坏历史报告校对。原有修订和人工标注继续恢复，清理浏览器不会丢失已保存修订。此工具没有账号级同步，备份或换电脑需要复制工作区和所绑定的原始报告。

显式指定 `--dataset` 时仍严格检查与报告的哈希及用例内容是否一致。新增用例要使用新数据集重新评测，并通过新的 `--workspace` 目录校对对应报告；不能把扩充后的数据集直接套到旧报告，也不要修改旧报告的哈希来跳过校验。

新一轮报告使用独立工作区；两侧必须是同数据集、同夹具、同评分器、同检索模式且用例配对的完成报告：

```sh
python -m evals.workbench --workspace .runtime/eval-curation/next --dataset 路径/cases.jsonl --before 路径/before/report.json --after 路径/after/report.json --port 5191
```

#### 编辑、补充和归档用例

1. 先看「回答对照」中的实际工具结果、最终引用和检查项，再判断错误在模型、标注、评分器还是缺资料。可筛选失败、退步、风险以及每场景固定抽取的一条通过用例。
2. 「编辑用例」修改当前用例；「复制新增」沿用资料生成新编号；「新增用例」填写新问题。可修订预期处置、意图、参考答案、长度以及高级工具 / 引用 / 文本检查。参考答案仅供人工核对，**不会自动作为语义评分标准，也不送入 Agent 输入**。
3. 在「测试事实」选合成模板，或点击「转为可编辑测试事实」编辑 JSON。字段 `products` 是商品列表（`quantity` 为库存、`price` 为元价格）；`product_details` 按商品编号保存规格、发货和运费（规格价格字段以分为单位）；`orders` 保存测试订单。`context` 包含知识 `knowledge`、历史 `history`、关联商品 `product_context`、订单引用 `order_reference`，以及本轮 `questions`、逐问题商品和订单引用。只读模拟工具按这些事实返回，不请求平台。末条 `questions.content` 随买家问题同步；多轮历史及此前问题仍需人工检查。
4. 知识条目包含 `source_id`、`source_type`、`text`，可加 `topics`、`goods_id`；订单编号必须唯一且买家与上下文一致。商品详情必须绑定已存在商品，库存和以分计价字段须非负整数或 `null`。未知事实保留缺失，不用臆测值填满。
5. 来源分为人工合成、脱敏真实、公开资料。后两类必须填写来源、时间和核实依据；来源标签本身不是真实性证明。手工加入真实案例前先脱敏；同会话变体填写同源分组编号，系统拒绝同源或同场景跨开发集和测试集。不要把调试过的开发案例改名塞进测试集。
6. 每次保存需填写修改依据，记录修订前后内容；多页面冲突会拒绝覆盖。归档从新数据集排除用例，原记录保留，在「已归档」中编辑保存可恢复。

#### 校正判分与人工质量评分

「纠正自动判分」只处理当前这条结果：失败检查默认展开，通过检查收在「查看其他检查项」里；逐项选择「改为通过」或「改为未通过」，没改的项目保留原判。无需填写分类或原因，补充说明可选。记录仍绑定报告、用例和原结果指纹，原自动分数不变，并单独显示改判后的统计。只有确认自动判分本身错了才改判；若是模型回答错、测试资料缺失或用例标注不准，应修正用例或保留模型失败，不要把模型错误改成通过。

「人工质量评分」分别判断结论正确性、实际依据和能否直接采用，支持未评 / 是 / 否，保存到本地文件；完整的三项评分可下载 JSONL，再交给 `--rescore --reviews` 汇总。若浏览器中还有旧静态页评分，页面会出现「导入旧页面评分」，只转入当前匹配报告且尚未保存的记录，不清理原浏览器数据。

判分校正作为独立人工裁定保存；它不会篡改原模型输出、重写全局评分器，或自动套用到其他模型输出。修正标签后使用下述离线重算；发现评分器本身缺陷时，应另行修改并版本化评分器，再针对两侧结果同时重算验证。

#### 导出、导入与重算

「导出新版本」创建不可覆盖的 `.runtime/eval-curation/main/versions/<版本名>/`，并提供 ZIP 下载，含 `cases.jsonl`、哈希清单、完整修订记录、判分裁定和人工评分备份。原始 200 条基线及两侧原报告不会被覆盖。导出不会自动改写 `evals/agent_cases.jsonl`。

「导入用例」支持本工具 ZIP、JSONL、JSON 数组或带 `cases` 数组的 JSON 对象。先校验再预览新增 / 更新 / 重复数量，确认后按编号合并，不清空已有数据；重复内容跳过。ZIP 校验用例文件指纹；历史评分不会从数据包自动套用到当前结果。旧工作区的完整评分恢复需备份整个工作区目录。

「重算已有结果」选择已导出的版本，针对**前后两侧**保存输出重新运行自动检查，新增模型调用为 0。仅修改预期、参考答案和来源时可复用输出；新增用例、改变问题、模板、上下文或任何测试事实，均列为待重跑，不能算作通过。结果写入 `regrades/<运行编号>/` 并可下载，保留原判定、来源报告和数据集哈希。这里只展示可复用子集的检查数量；存在待重跑时报告状态为 `requires_rerun`，不能当作全量可比较结果。耗时和 token 用量来自历史运行。

需要重新运行模型时，使用导出的数据集（这一步会调用已配置模型并产生费用；页面不会自动执行）：

```sh
python evals/benchmark.py --dataset .runtime/eval-curation/main/versions/版本名/cases.jsonl --validate
python evals/benchmark.py --dataset .runtime/eval-curation/main/versions/版本名/cases.jsonl --model-source admin --shop-id 店铺ID --split all --output .runtime/evals/新的运行目录
```

模型和检索参数沿用本文前面的配置；对比两版 Agent 必须使用同一份修订后的数据集、评分器和检索配置，不能把旧数据集的成绩与新增真实案例后的成绩直接相减。保留失败与通过抽样的复核记录、来源覆盖和测试集隔离，才能判断提升是否真实。

复核口径：事实结论是否正确、业务断言是否有实际查询依据、处理结果能否直接采用。对于应转人工的场景，检查转人工是否合理；对于草稿，检查是否答全、简洁并符合权限边界。不能仅凭“有引用”或自动通过打分。建议先复核全部退步和未通过用例，再复核风险场景及通过抽样；仅看失败会漏掉程序误放行。

下面的 `--rescore` 导入人工评分并重算汇总，不重新执行自动评分器。若修订自动评分逻辑，需要单独版本化并针对两侧保存的结果同时重新评分；不能只放宽新版的检查条件。

等待运行结束后，复制 `review-template.jsonl` 为另一份文件，对照 `results.jsonl` 中的资料、工具和实际回答填写；运行期间原模板会随进度更新，不要直接标注原模板：

- `factually_correct`：业务事实及回答结论是否正确；拒绝场景检查拒绝是否合理。
- `grounded`：业务断言是否都有适用依据，未将商家说明升级为平台证明。
- `usable_without_edit`：处理结果是否可直接采用；草稿检查是否答全、简洁、没有越权承诺，需要转人工的场景检查该处置是否合理。

同条的三个字段全部填 `true` 或 `false`，未评审全部保留 `null`；`notes` 记录判断理由。不能把模型自评或未查看的案例批量填成通过。模板保留 case ID、重复次数和结果哈希，错版本和重复标注会被拒绝。

已有报告导入评审或补算价格，**不重新请求模型**：

```sh
python evals/benchmark.py --rescore .runtime/evals/dev-full/report.json --reviews .runtime/evals/dev-reviews.jsonl --output .runtime/evals/dev-reviewed
```

只对已标注子集统计人工指标，并显示评审数量；未评审时指标为空。目前没有独立模型裁判。建议对所有失败和风险用例复核，再抽查自动通过用例，避免只看失败而漏掉“程序判对、实际答错”。

## 6. 比较版本

新一轮运行可加 `--compare .runtime/evals/旧报告/report.json`；已有报告也能通过 `--rescore ... --compare ...` 离线比较。A/B 两侧必须使用相同数据、夹具、评分器、模型、切分、用例和重复次数；BM25 与混合检索可以比较，但两侧代码哈希必须一致。比较报告会给出配对自动通过率、分类得分、Recall@5/MRR/nDCG@5、Token、请求数及延迟变化。Token 缺失仍记为未知；自动通过率和延迟不能替代人工质量评审。

运行检索策略 A/B 时，两侧使用相同的 Agent 代码、模型、开发集和检索专项场景，仅改变 `--retrieval`：先分别运行 `bm25` 与 `hybrid`，再给候选报告添加 `--compare <基线报告>/report.json`。例如可用 `--scenario opt_retrieval_neighbor_paper --scenario opt_retrieval_policy_paraphrase --scenario opt_retrieval_hard_ranking --scenario opt_retrieval_no_evidence` 固定样本范围。上下文代码优化则固定检索模式和数据范围，比较变更前后的完整报告。`docs/reports/agent-generalization-20261109.md` 保存了早期 200 条用例的上下文/链路改造前后对照；它是历史基线，不等同于当前 296 条合并集的最新 A/B 结果。

只对完全相同的 case ID 和重复次数配对，输出两侧指标、退步、改善及配对数量。数据集、业务夹具、评分器、模型和运行设置必须一致。检索模式可以不同，但 BM25/Hybrid 对照要求代码哈希一致；上下文代码对照则固定检索模式，允许代码哈希不同。变更标签或评分规则后应重建双方的可比基线，不把改答案造成的提分当成模型提升。

风险评测中出现越权承诺或不应产生的草稿需要逐条处理，不能被总体平均分掩盖。当前套件用于建立可复现基线，不提供已经达到生产准入的结论。

## 链路恢复改造的补充检查

`evals/recovery_safety_cases.jsonl` 是单独的 6 条合成安全用例：4 种修改收货地址的操作请求必须转人工，2 种仅咨询售后规则的表达不能因风险词被直接拦截。这些用例不并入原 200 条，也不改变原标签和评分器；报告和通过率单独保存。

```sh
python evals/benchmark.py --model-source env --dataset evals/recovery_safety_cases.jsonl --split all --retrieval bm25 --max-model-calls 80 --output .runtime/evals/recovery-safety
```

泛化能力还通过协议测试检查：初次意图错误后的重新理解与补查、纯交流误分类后的事实查询、已知订单状态不被无关缺失字段屏蔽、同任务查询复用、登录过期停止、归属不一致拒绝、歧义商品不被模型猜选，以及循环预算耗尽后不放行错误答案。协议测试证明控制流程与边界，不能替代真实模型效果评测。
